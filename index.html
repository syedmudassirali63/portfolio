SYSTEM ARCHITECTURE

The gateway layer sits between client applications and backend microservices. Behind an edge cache (Varnish) that also enforces WAF and security rules, a set of stateless gateway services handles routing, page composition, core orchestration and AI-driven assistance, while a dedicated content query service and a central configuration server support them. An in-memory cache (Redis/Valkey) further reduces calls to backend services.

Key design decisions

DecisionWhy
Separate gateway servicesProxy, page composition, main and AI services scale and change independently while clients see one consistent entry point.
Two-level cachingVarnish edge cache serves repeat responses before they reach the gateway; Redis/Valkey caches hot data inside it. Together they cut backend and database calls and drove the 50% performance gain.
WAF and security rules at the edgeMalicious or malformed traffic is filtered in Varnish before it reaches the gateway services, which reduces load and attack surface.
Dedicated content query serviceContent queries run on a search index and stay separate from configuration services, so each can scale and change on its own.
Kafka for eventsReliable, decoupled communication across Nano and Micro services and to the push dispatcher.
Central configuration serverConfiguration is managed in one place and applied to all gateway services, so changes are consistent and need no redeploys of each service.

REQUEST FLOW

How a typical authenticated content request moves through the platform.

Authentication & token lifecycle

  • OIDC and OAuth2 login; JWT access tokens with refresh tokens and refresh token rotation.
  • Cookie lifecycle handled centrally: secure flags, platform-specific SameSite policy, domain scoping and expiry.

Real-time push

  • Events flow through Kafka to the WS Message Dispatcher (Node.js, Socket.IO), which pushes messages to connected client devices and handles automatic reconnection.

WS MESSAGE DISPATCHER ARCHITECTURE

A real-time push system that delivers messages to connected devices over WebSockets. Multiple identical pods run side by side, so capacity grows by adding pods.

How it works

  • The push message service publishes each message to a delivery topic. Every dispatcher pod receives it and delivers it to the devices connected to that pod.
  • Each pod reports successful deliveries to a success queue, so the push service knows what reached the device.
  • Messages that could not be delivered are kept in a message store. When a device connects, the pod posts an event to the on-connect queue and the push service resends what is waiting.
  • Pods are stateless and horizontally scalable; devices reconnect automatically to any pod.

AUTOMATION TEST FRAMEWORK

A Node.js-based integration test framework that runs API test collections on every nightly build and reports pass/fail results directly into Zephyr on Jira Cloud or on-premise Jira.

Execution flow

1The collection runs through the collection runner, Postman, or Newman and the command line.
2URLs and other properties come from the environment file. An environment flag (is_jira_cloud_enabled) selects Jira Cloud (true) or on-premise Jira (false).
3Every test case can have its own input data, made up of scenarios and channels.
4Helper functions for pre- and post-processing of requests are hosted separately in core.js and scripts.js.
5A local server generates JWTs from the method and URL given as input (Jira Cloud only).
6Zephyr execution details such as cycle, steps and version are fetched and saved for later use.
7All APIs in the collection run sequentially.
8Step results are updated in Zephyr. On an error, it points to the last step that failed.
9The execution is marked PASS or FAIL based on the step results of the earlier APIs.

CASE STUDIES

1. Improving platform performance by 50%

Problem: Heavy traffic from many clients meant repeated backend and database calls for the same data.

Approach: Introduced Varnish edge caching (with WAF and security rules) and Redis/Valkey caching for frequently accessed data, and optimized Elasticsearch queries.

Result: 50% improvement in overall performance on a product delivered to clients with 40M+ users, with fewer microservice calls and database round trips.

2. Enterprise-grade authentication framework

Problem: Several client platforms needed consistent, secure login and session handling.

Approach: Built an OIDC / OAuth2 / JWT framework with refresh token rotation and a central cookie management system.

Result: Compliant with enterprise security requirements across client platforms; SAST/DAST findings assessed and remediated.

3. Dynamic content query engine (DCQ)

Problem: Content availability rules (filters, nested queries, scheduling) differed by client and changed often.

Approach: Designed the DCQ service on Elasticsearch with Mustache query templates, pagination and minute-level time precision, kept separate from configuration microservices.

Result: Flexible per-client queries without code changes to the core flow.

4. Real-time WS Message Dispatcher

Approach: Built a Socket.IO push server fed by a Kafka consumer, with guaranteed delivery semantics and automatic reconnection.

Result: Real-time message delivery to connected devices at scale.

5. Integration test automation framework

Approach: Node.js framework that runs Postman collections (Newman) in nightly builds, supports Jira Cloud and on-premise Jira through an environment switch, and writes step and execution results to Zephyr. See the framework page for the full flow.

Result: Stakeholders get daily pass/fail visibility without manual test runs.
